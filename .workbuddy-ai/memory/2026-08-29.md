feature checklist — it is four judgements:

1. **Problem taste** — did you pick something that actually matters
2. **Build quality** — does it run, is it structured, would you trust it

## Repo hygiene + security cleanup (public repo — mattered)

The repo is public at github.com/Krishna-10-7/buildathon. Found and fixed:
- **1106 committed Chromium profile files** (GPU/shader cache, BrowserMetrics,
  cookies). 13.7 MB of junk. The `.gitignore` rules already existed but the
  files were committed BEFORE the rules were written, so they were still
  tracked — `.gitignore` never untracks. Fix was `git rm -r --cached`.
- **`app/artifacts/persona_identities.json`** held three real-format Indian
  mobile numbers. Untracked.
- **Razorpay test key id `rzp_test_...`** was committed in README.md and
  MEASUREMENT-DAY.md. Redacted in both, then history rewritten.

Result: 1301 → 201 tracked files. Because the leak was already pushed
(HEAD == origin/main), a working-tree redaction was not enough — amended the
single commit and force-pushed with `--force-with-lease`. Old commit is still
recoverable from reflog if ever needed.

Lesson worth keeping: **`.gitignore` is not retroactive.** Any time rules are
added, run `git rm -r --cached <path>` for already-tracked matches.

## Key-rotation root cause + one-command fix (analysed, not yet implemented)

User asked: "I have to change the Razorpay test API key everyday or I get
captcha errors". Root cause: Razorpay test-mode risk stack is
**stateful and velocity-keyed** — every Checkout JS load against a key id
accumulates bot-shaped history; past threshold it challenges. Own data
confirms: 0% challenge in first third of a 40-session clean run, 23.1%
in second third, ~90% under a later high-frequency batch. Fresh key
≈ 10–13 clean checkouts. Two known mitigations: (a) s2s payment API
ruled out by direct probe on this account
(`app/scripts/probe_s2s_payment.py` — `400 BAD_REQUEST_ERROR "The
requested URL was not found on the server"`), (b) decouple `/demo` to
**replay** verified real trips. Both fleet and demo key slots proposed.
Wrote `research/10-key-rotation-and-risk-escalation.md` with the full
analysis.

`MANDATE_SECRET` must stay pinned across rotations — `app/bazaar/mandates.py:30`
falls back to `f"{rzp_key_secret}:mandates-v1"` if unset, so rotating
`RZP_KEY_SECRET` without pinning would silently invalidate every
outstanding mandate signature. Verified pinned on both hosts
(43-char hex on local + VM1).

The `rotate_keys.py` automation described in research/10 is NOT YET WRITTEN.
That and the `/demo` replay-by-default switchover are the next concrete
ships for this thread.
